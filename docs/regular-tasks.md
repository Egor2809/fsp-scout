# Регулярные задания

Восемь операций контракта реализованы в TasksController. Работодатель публикует
кодовое задание, ревью или описание подхода с рубрикой. Критерии должны быть
уникальными, иметь веса 0..1 с суммой 1; срок должен оставлять время
на выполнение. time_limit_min — оценка длительности, общий срок задаёт deadline_at.
Контракт не содержит отдельной команды запуска таймера.

Maintenance worker назначает до 25 кандидатов на задание. Подходят только
подтверждённые специализация и грейд, согласия personal_data/profile_visibility,
доступность для поиска и отсутствие компании в скрытых. Общий интервал между
назначениями — 14 дней, включая задания других компаний и истёкшие назначения.
Повторная проверка выполняется под блокировкой Candidate; параллельные worker
используют SKIP LOCKED. Проверка заданий идёт с ротацией, чтобы неподходящие старые
задания не блокировали новые. Эти транзакции ещё требуют проверки на PostgreSQL.

Кандидат сдаёт решение один раз. Уникальность защищена БД; пустые ответы,
чужие назначения, неверный язык и истёкший срок отклоняются. Код хранится как данные
и пока не исполняется. В outbox создаётся task.submitted; LLM-оценщик и обработчик
этого события ещё не подключены. llm_score остаётся null, оценка по длине не используется.

Финальную оценку 0..100 выставляет владелец задания. Каждое сохранение аудируется.
Порог решённого задания — 75. Сигнал пересчитывается по уникальным сохранённым
решениям, поэтому повторная оценка не увеличивает счётчик; исправление вниз отзывает
этот вклад. Свежесть — 30 дней от сдачи решения, не от повторной оценки.
Свежесть проверяется и при чтении карточки, без ожидания очередного задания.

Решение не раскрывает контакты автоматически. Владелец получает анонимную карточку;
из текста и кода в представлении работодателя удаляются распознаваемые контакты.
Для приглашения source.type=task_submission требует решение именно этого кандидата
на задание текущей компании. Принятие приглашения раскрывает контакты обычным путём.

## Проверки

Чистые тесты проверяют рубрику, 14-дневную границу, пересчёт и истечение сигнала.
integration/tasks.test.mjs проверяет живой API, назначение worker, одновременную
сдачу, доступ другой компании и пересмотр оценки без накрутки счётчика.
Этот сценарий ещё не запускался. Нужны три JWT из инструкции vacancies.md,
отдельный кандидат с подтверждённой категорией, согласиями и без недавнего назначения,
работающая очередь и worker. Сценарий оставляет тестовое задание с часовым сроком.
Запуск: cd backend; npm run test:integration.

## Статистика приглашений

GET /invitations/stats выбирает инвайты своей компании, отправленные за days
(7..365, по умолчанию 90). Воронка считает достижение этапа по истории, один раз на
инвайт. Acceptance rate = accepted/(accepted+declined). Медиана — время до первого
ответа accepted/declined/postponed; просмотр не считается ответом. Для чётного числа
наблюдений усредняются два центральных значения. Пустая выборка: rate=0, median=null.
