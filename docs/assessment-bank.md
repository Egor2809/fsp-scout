# Банк и проверка ответов

assessment/live-bank.ts содержит 15 параметризованных семейств для будущего рабочего
банка: SQL COUNT/NULL и JOIN, очередь, token bucket, критический путь CI,
комбинации конфигураций, границы диапазона, SLO, среднее, F1, вложенный цикл,
дерево, CSS box model, dp/px и пакетные worker. Экземпляры воспроизводимы по seed;
правильный ответ вычисляется из параметров. a/b — экспертные априорные значения,
эмпирической калибровки нет. Каталог ещё не подключён к сессиям оценивания.

instantiate возвращает отдельные publicItem и expectedAnswer. В publicItem нет
familyId, seed, параметров генератора, a/b или ключа ответа. Он содержит только
поля TestItem из OpenAPI. Описание уровня сложности строится по позиции b в каталоге.

assessment/grading.ts проверяет single/multiple choice, текстовый вывод и числовой
ответ с явными допусками. Дубликаты, неизвестные варианты, смешанные форматы,
пустой ответ, превышение длины, NaN/Infinity и выражения вместо числа отклоняются.
Пропуск даёт неверный ответ. Код требует реальной песочницы, открытый текст —
явного ревью; они возвращают pending, а не фиктивный correct. Эту проверку ещё
предстоит связать с POST answers и транзакциями сессии.

## Витрина

GET /assessment/families и /assessment/families/:id используют отдельный каталог
трёх примеров из frontend: Go append, изменяемый default Python и оконная SQL.
Семейства витрины не пересекаются по ID с будущим рабочим банком.
calibration_n=0, exposure_rate=0; описание прямо говорит об отсутствии калибровки.
На витрине корректный ответ намеренно раскрывается по контракту.

## Ограничения

15 семейств недостаточно для полноценного CAT по всем специализациям. Для гарантии
ёмкости банка при полной длине 18 заданий и потолке экспозиции 20% требуется
не менее 90 подходящих семейств на специализацию. bankInventory показывает дефицит;
это проверка ёмкости, а не доказательство покрытия компетенций или фактической
экспозиции. Новые варианты одного шаблона нельзя считать отдельными семействами.

Нужны расширение содержания, практические задания, реальные сессии и результаты,
пилот/калибровка, наблюдаемая экспозиция, сохранение истории категорий и sandbox.
Текущие числовые параметры и синтетическая симуляция не доказывают качество теста.

## Проверки

Юнит-проверки включают 1500 экземпляров, структуру публичного объекта, правильные
и неверные числовые ответы, независимый перебор JOIN/вложенного цикла и пошаговые
симуляции очереди/token bucket. Отдельно проверяются перемешивание SQL-вариантов
витрины и отсутствие выдуманной калибровочной выборки.
Эти проверки не заменяют экспертную проверку содержания и интеграцию на БД.
