# Техническая документация

## Назначение и границы

Скаут связывает работодателей с анонимными профилями ИТ-специалистов.
Доверенные сигналы отделены от заявленных: категория возникает из теста,
достижения ФСП влияют на подбор при проверке и согласии кандидата,
внешние резюме оцениваются без приписывания им этих сигналов.
Документ описывает архитектуру, API, тест, подбор, развёртывание и валидацию.

## Архитектура

React + TypeScript + Vite → `/api/v1` NestJS → PostgreSQL через Prisma.
Keycloak выдаёт OIDC-токены по Authorization Code + PKCE; API проверяет JWT
и JWKS. Redis/BullMQ обслуживает фоновую очередь. Отдельный worker проверяет
код через Piston, назначает регулярные задания и обрабатывает удаление аккаунтов.
PDF-резюме обрабатываются Python-инструментами в runtime-контейнере backend.
Frontend раздаёт nginx; на публичном стенде Caddy завершает TLS.

## API и данные

Источник контракта: `contracts/openapi.yaml`; матрица операций:
`docs/api-matrix.md`. Входные тела проверяются Zod-схемами; ошибки возвращаются
в формате RFC 9457. Снимки моделей frontend/backend проверяет
`npm run check:contract` (232 файла моделей).

Основные области: профиль кандидата/компании, согласия, потребности,
поиски, тесты и ответы, приглашения, вакансии/отклики, регулярные задания,
достижения ФСП и внешняя оценка ранжирования. Схема хранения и SQL-миграции
находятся в `backend/prisma`. Не заменяйте миграции командой `db push` при сдаче.

`POST /api/v1/eval/rank` принимает вакансии и резюме с идентификаторами,
возвращает ранжирование и факторы. Нужна роль employer/admin. JSON Resume
исключает поля имени, контактов и адреса из текстового подбора. CSV-выдача
экранирует кавычки и нейтрализует формулы ячеек.

## Тестирование кандидата

В исходниках реализованы выбор семейств CAT, 3PL/EAP с учётом угадывания, ограничения экспозиции,
контроль компетенций, практика с кодом, серверная проверка ответов,
последовательные состояния сессии и защита от повторных ответов.
Ключи объективных заданий остаются на сервере. Необработанный код или
свободный ответ не может автоматически стать подтверждённым верным ответом.
Отсутствие или провал обязательной практики не заменяется высоким CAT-результатом.

Банк `expert-bank-20261010-v6`: 244 параметрических семейства — 160 с числовым ответом, 70 с выбором ответа (у каждого пул формулировок с разными правильными вариантами) и 14 канареек, по две на специализацию.
Параметры a и b — экспертные приоритеты; калибровка по реальным ответам предусмотрена после пилота. Проверка
песочницы требует реального Piston с установленными версиями рантаймов.
Без Piston практика отключается, и категория подтверждается адаптивным блоком.

## Подбор и объяснения

Публикация требует подтверждённую категорию и согласие. Учитываются скрытые
компании, доступность, формат, город/релокация и обязательные навыки.
Один грейд ниже запроса допускается со штрафом 15 баллов и пометкой в chips.
Специализация остаётся строгой. Совпадение с выбранным грейдом имеет приоритет
над соседними выбранными категориями. Итог ограничен диапазоном 0–100,
отображаемые вклады суммируются в итоговую оценку.

Внутренний подбор использует покрытие навыков, Jaccard, отрасль, условия,
перцентиль, подтверждённые навыки, регулярные задания и достижения ФСП.
Внешний подбор использует покрытие словаря и BM25. Эти два режима различаются
доступными доказательствами и не должны сравниваться как одинаковые модели.

## Приватность и контроль доступа

Контакты раскрываются в контексте конкретной компании после согласия.
Внешнее резюме не доказывает личность, тест или достижение. Подтверждение
ФСП принимает подписанные webhook-данные с HMAC по исходным байтам.
Удаление личности учитывает issuer и subject; worker обращается к Keycloak
с отдельными служебными credentials. Шифрование контактов на уровне полей
БД по пункту 4.5 плана ещё не внедрено.

## Развёртывание

Локально: `docs/local-deployment.md`; публично: `docs/public-deployment.md`.
Образы backend разделяют build/migrate/runtime. API и worker работают без root,
с read-only файловой системой и временным `/tmp`. Compose ожидает PostgreSQL,
Redis и завершение миграций. Готовность API проверяется `/api/v1/ready`;
этот endpoint не заменяет отдельную проверку OIDC и Piston.

## Валидация

Валидация воспроизводится командой `npm run eval` (backend), подробности в `docs/validation.md`.
На 2000 синтетических кандидатах с независимым генератором ответов (3PL со сдвинутыми параметрами):
точный грейд 58,5% (в продуктовом сценарии 62,6%), взвешенная κ 0,82, ложные отказы 21,7%, r(θ̂, θ) 0,88, test-retest κ 0,72.
При сливе ключей всех экземпляров θ̂ завышается на +0,65 против +2,68 у фиксированного теста.
Подбор на отложенной выборке: nDCG@10 0,578 против 0,309 у BM25, P@10 0,672 против 0,361.

## Какие модели, как и зачем

Сейчас LLM не участвует в подтверждении навыков и не подключена к генерации
боевого банка. Планируется GigaChat или YandexGPT для черновиков: постановка,
навык, варианты ответа, объяснение и эталон → экспертная проверка →
изолированная проверка эталона → пилот → калибровка сложности и времени.
До этой проверки черновики не должны попадать в подтверждающий тест.
Версия модели, prompt, параметры, рецензент и дата должны сохраняться
в происхождении задания; реальные персональные данные в prompt не передаются.
Используются только российские модели, как рекомендовал заказчик: основная — GigaChat,
резервная — YandexGPT. Обе работают в российском контуре, трансграничной передачи данных нет. Сгенерированных и прошедших
экспертную проверку заданий в этой итерации нет: банк из 160 семейств составлен экспертно.

## Защита от фиктивных вакансий

- Вилка в приглашении и вакансии обязательна, верхняя граница не больше чем в 1,6 раза выше нижней.
  Вилка ниже ожиданий кандидата не отправляется, а порог кандидата компании не раскрывается.
- Квота приглашений на неделю: база плюс бонус до +10 за долю принятых приглашений за 90 дней
  и штраф −2 за каждое приглашение, отозванное после согласия кандидата. Квота не меньше 1.
- Кандидат видит надёжность компании в приглашении: число приглашений за 90 дней, долю принятых
  и число отзывов после согласия.
- Контакты кандидата раскрываются только компании, приглашение которой он принял.

## Прокторинг

Во время теста браузер считает вставки из буфера и потери фокуса вкладки и отправляет их
вместе с каждым ответом. Сервер сам измеряет время от выдачи задания до ответа. При
завершении теста по этим данным строятся флаги `paste`, `focus_loss` и `fast_correct`
(правильный ответ заметно быстрее типичного для этого семейства). Флаги информационные:
они не меняют грейд, потому что события браузера не доказывают нарушение.
Ключи ответов хранятся только на сервере, у каждого кандидата свои параметры заданий.
