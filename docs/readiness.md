# Готовность сервисов

GET /api/v1/health проверяет работу процесса. GET /api/v1/ready параллельно выполняет PostgreSQL SELECT 1 и Redis PING через BullMQ-соединение с общей конфигурацией REDIS_URL. При сбое или ожидании дольше двух секунд возвращается 503 application/problem+json без деталей подключения. Одновременные запросы используют один текущий probe. Таймер ответа не отменяет уже отправленный SQL-запрос; нужны серверные лимиты PostgreSQL и контроль пула.

Redis command/connect timeout — 1500 мс, offline queue выключена. После тайм-аута сохраняется общий неуспешный probe до фактического завершения обоих I/O: следующие проверки не создают дополнительные зависшие SQL-запросы. Затем новая проверка может подтвердить восстановление. При остановке NestJS соединение принудительно закрывается. Redis использует ту же очередь assessment-grading, но ready не доказывает присутствие worker, актуальность scheduler, доступность Piston, Keycloak или достаточность банка тестов. Нужен отдельный мониторинг worker и возраста неоценённых событий.

Исходный API BullMQ 5.58.5 проверен: https://github.com/taskforcesh/bullmq/blob/v5.58.5/src/classes/queue-base.ts

77 независимых от NestJS модульных тестов проходят, включая тайм-аут, запрет повторного I/O и восстановление общей проверки. Сам сервис readiness и восстановление после отключения PostgreSQL/Redis ещё не проверены на работающем окружении; эти тесты не доказывают его runtime-готовность.
