# Уточняющий блок по своему решению

Новая policy содержит approachTotal=1. Worker создаёт уточняющий вопрос только
после успешного выполнения кода на девяти проверках практики и дополнительном
входе-пробе. Десятая проверка выполняется тем же кодом в том же закреплённом
runtime. Поэтому ожидаемый ответ вопроса совпадает с проверенным выводом
программы; в интерфейс он не передаётся.

Вопрос имеет block=approach, type=short_answer. Он показывает собственный
принятый код и новый JSON-вход, просит предсказать одно целое число без повторного
запуска. Ожидаемое число хранится только в expectedAnswer. Seed и параметры
не входят в publicItem. В интерфейсе /run недоступен для short_answer.

Запись правильности практики, вопроса и завершения outbox выполняется одной
транзакцией под fencing-проверкой. Повторная доставка не создаёт второй вопрос.
Next возвращает сохранённый вопрос как обычное текущее задание; Answer проверяет
число серверным numeric grader. Для подтверждения категории нужны правильная
практика и правильный уточняющий ответ. Пропуск/ошибка вопроса сохраняют прежнюю
категорию. При провале практики вопрос не создаётся, результат уже failed.
Старые сессии без approachTotal не подтверждают новую категорию.

Прогресс фронтенда показывает дополнительный сегмент, когда блок C выдан.
Генератор проверен на 500 вариантах. Всего проходят 70 модульных тестов;
в реальной песочнице кандидатский код этими тестами не исполняется.

Это ограниченный сигнал понимания программы, а не доказательство авторства:
кандидат может вычислить ответ по условию или воспользоваться внешним инструментом.
Свободное объяснение архитектуры, вопросы по конкретным переменным/веткам кода,
оценка объяснения и пилот ложных срабатываний остаются отдельной работой.
Реальная цепочка API → outbox → worker → Piston → вопрос пока не проверена.
