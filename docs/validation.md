# Валидация теста и подбора

Отчёт собирается одной командой из `backend`:

```bash
npm run eval   # ~40 с, seed 20261010, результат в backend/eval/validation-report.json
```

Скрипт `backend/eval/validate.ts` вызывает боевой код и ничего из него не копирует: выбор задания
`selectFamily`, оценку `scoreCompletion` и `scoreOutcome`, контроль экспозиции `exposure`, банк
`LIVE_BANK` с генерацией экземпляров `instantiate`, проверку ответа `gradeAnswer`, подтверждение
навыков `confirmedSkills`, перцентиль `empiricalPercentile`, фильтры и скоринг подбора
`hardFilters` и `explain`, текстовый ранжировщик `/eval/rank` (`rankExternal`), метрики
`rankingMetrics`. Цифры в этом документе взяты из отчёта и вручную не правились. Старая
симуляция `eval/simulate.ts` удалена: в ней ответы генерировала та же модель, которой их потом
оценивали, а банк был выдуманным.

## Методика

**Всё синтетическое.** Реальных кандидатов с известным «настоящим» уровнем у нас нет, как и у
конкурентов. Поэтому отчёт проверяет, как алгоритм ведёт себя на популяции со скрытой истиной.
Это не доказательство того, что тест работает на живых людях.

**Генератор ответов не совпадает с оценщиком.** Оценщик знает только экспертные `a = 1,2` и `b`
из банка и считает EAP по 3PL: угадывание c = 0 у числовых, 1/число вариантов у single_choice, 0,05 у multiple_choice. Ответы генерирует 3PL с другими параметрами семейства:
`a_true = a × U(0,7; 1,3)`, `b_true = b + U(−0,4; 0,4)`, угадывание `c = 0,02` у числовых (в банке `v6` 160 числовых
семейств, 70 с выбором ответа и 14 канареек; для выбора `c` как у оценщика). Реальный сдвиг: |Δa|/a в среднем 0,16, |Δb| 0,20.
Оценщик об этих сдвигах не знает.

**Популяция теста.** 2000 кандидатов, θ ~ N(0,1), поровну по 7 специализациям. Истинный грейд
определяется по боевым порогам: ниже −1,2 — «ниже junior» (240 человек), junior 453, middle 642,
senior 452, lead 213. Заявленный грейд: 60% указывают истинный, 20% на ступень выше, 20% на
ступень ниже. Сессии идут подряд с общим счётчиком экспозиции, как в продакшене: потолок 0,4,
окно считается по специализации. Политика теста боевая: 8–14 заданий, SE ≤ 0,4, top-3,
обязательное покрытие компетенций, в которых у специализации не меньше трёх семейств. Практический блок с кодом не
моделируется, `practiceTotal = 0`, как при выключенной песочнице.

**Грейд по θ̂** — это полоса, в которую попала оценка. Пять классов: «ниже junior» и четыре
грейда. **Решение теста** — подтверждён ли заявленный грейд (`outcome ≠ failed`, то есть
P(θ ≥ порог) ≥ 0,6). **Продуктовый сценарий**: кандидат идёт по подсказкам системы. Провалил —
пересдаёт ступенью ниже, получил `passed_confident` — пробует ступенью выше. Всего не больше
четырёх попыток. Итоговый грейд — последний подтверждённый.

ДИ везде — перцентильный бутстрэп, 1000 повторов, 95%. Для теста ресэмплируются кандидаты, для
подбора — потребности.

### Что исправлено по итогам валидации

Сессия больше не обрывается на обязательном покрытии. Раньше она требовала все компетенции
банка, в том числе те, где одно-два семейства, а потолок экспозиции 0,4 их быстро исчерпывал:
48% сессий заканчивались `coverage_unavailable` (409 на `/next`), точный грейд был 51,6%,
ложных отказов 64%. Теперь обязательны только компетенции, где семейств не меньше
`ceil(1 / maxExposure) = 3` (`requiredCompetencies` в `live-bank.ts`). Если покрытие всё равно
упирается в экспозицию, компетенция снимается с обязательных для этой сессии
(`selectWithWaiver`, поле `waivedCompetencies` в политике сессии). Так случилось в 51 сессии
из 2000, и все они дошли до 14 заданий.

## Слив банка

600 «слабых» кандидатов (θ ниже порога middle, в среднем −1,10) заявляют middle. Любое
подтверждение у них ложное. Утекает k% семейств банка специализации. Сценариев два.

* **Утечка ключей экземпляров.** Злоумышленник собрал по 300 реальных экземпляров каждого
  утёкшего семейства с ответами (генерируются настоящим `instantiate`). Если формулировка
  совпала дословно, он берёт ответ из дампа, иначе вписывает самый частый ответ дампа. Ответ
  проверяет боевой `gradeAnswer`.
* **Утечка метода решения.** Кандидат знает, как решать утёкшие семейства, и решает их верно.

Фиксированный тест — те же 12 заданий с постоянными числами для всех, поэтому для него
утечка ключа и утечка метода совпадают. Завышение θ̂ считается относительно того же
кандидата без утечки.

| Утечка | CAT: ключи экземпляров | CAT: метод решения | Фиксированные 12 |
|---|---|---|---|
| нет — ложные подтверждения | 15,0% | 15,0% | 23,3% |
| 25% — завышение θ̂ / ложные подтв. | +0,13 / 23,3% | +0,66 / 53,8% | +0,64 / 71,8% |
| 50% | +0,27 / 31,2% | +1,45 / 86,5% | +1,24 / 100,0% |
| 100% | **+0,62** / 53,3% | +3,14 / 100,0% | **+2,68** / 100,0% |

ДИ для каждой ячейки есть в отчёте. Выводы:

* Параметризация режет вред от слитых ключей вчетверо: +0,62 против +2,68 у фиксированной
  формы при полном сливе, +0,27 против +1,24 при сливе половины. На банке `v3` без заданий с выбором
  было +0,64, на `v4` +0,97: ключи заданий с выбором переносились между экземплярами. В `v6` у них
  пулы формулировок с разными правильными вариантами.
* От утечки метода параметризация не защищает, и не должна: знать метод и значит уметь решать.
* **Дамп банка.** В банке `v4` правильный вариант в заданиях с выбором был одинаков во всех
  экземплярах, и ответ по дампу из 300 экземпляров угадывался в среднем в 52% случаев. В `v6` у
  каждого семейства с выбором пул формулировок с разными правильными вариантами: средняя
  угадываемость 26%, выше 50% — у 48 из 244 семейств (было 115). Остались семейства со 100%
  угадыванием, например `live-srcset-choice`, `live-closure-var-let`, `live-cidr-hosts`,
  `live-touch-target`, `live-decision-table`.

### Канарейки
14 канареечных семейств (по 2 на специализацию) ставят флаг `leak_suspected`, если канарейка
решена верно и аномально быстро (z < −2,5 по логнормальной модели времени), а оба соседних
обычных задания решены неверно. Флаг не меняет грейд. Модель времени в симуляции: медиана
семейства 45 с, разброс σ = 0,5 в логарифме, ответ по готовому решению в 8 раз быстрее.

| Сценарий | Сессий с канарейкой | Флаг |
|---|---:|---:|
| Честные кандидаты | 43,5% | 0,0% |
| Слив ключей экземпляров, 100% | 50,3% | 0,0% |
| Готовый решатель для 25% семейств | 55,8% | 4,7% |
| Готовый решатель для 50% семейств | 53,2% | 2,5% |
| Готовый решатель для всех семейств | 44,3% | 0,0% |

Ложных срабатываний нет, но ловит правило мало. Слитые ключи экземпляров к новым экземплярам
канарейки не подходят, поэтому дамп канарейку не решает вовсе. Готовый решатель для всех семейств
не оставляет неверных соседей. Правило консервативное: оно отмечает только явные случаи для
проверки человеком.

## Подбор

**Данные.** Два независимых мира: dev для подбора формулы и holdout для отчёта. В каждом
1750 кандидатов (по 250 на специализацию) и 210 потребностей работодателей. У кандидата скрыты
θ, набор навыков, которыми он реально владеет (4–7 из 14 самых частых навыков специализации), и
уровень владения каждым (θ + N(0; 0,6)). Наблюдаемое резюме шумное: 10% реальных навыков не
указаны, четверть кандидатов «накручивает» резюме (3–5 лишних навыков, грейд на ступень выше,
повторы ключевых слов). Каждый кандидат проходит **боевой тест** по продуктовому сценарию.
Ответы зависят от θ и от владения навыками, привязанными к семейству, поэтому тест в этой части
многомерный, а оценщик нет. Из теста берутся подтверждённая категория, перцентиль внутри
категории (`empiricalPercentile`), SE и подтверждённые навыки. ФСП-достижения и регулярные
задания тоже генерируются из θ с шумом.

**Золотая релевантность** считается только по скрытой истине и не использует наблюдаемые поля
формулы: ни зарплату, ни отрасль, ни формат, ни заявленные навыки. Метка 0–3 равна
`соответствие грейда × (0,7 × доля must-навыков + 0,3 × доля nice-навыков)`. Навык засчитывается,
если им реально владеют на уровне не ниже порога грейда − 0,4. Соответствие грейда в основной
разметке: совпал — 1, на ступень выше — 0,85, на две выше — 0,6, на ступень ниже — 0,3.
Релевантен тот, у кого метка ≥ 2. Для P@10 и MRR@10 берётся именно этот порог, nDCG@10 считается
по градуированной метке. Порог переквалификации — произвольное решение авторов, поэтому
приведены ещё две разметки: строгая (выше на ступень 0,7, на две 0) и мягкая (любой грейд не
ниже нужного — 1). Честно о порядке работы: первой была строгая разметка. После первого
прогона стало видно, что вывод зависит от штрафа за переквалификацию. Тогда основной сделали
промежуточную, строгую оставили и добавили мягкую. Формулу подбора меняли уже после этого,
глядя только на dev.

Системы:
* **наш подбор** — боевые `hardFilters` + `explain`;
* **BM25** (k1 = 1,2, b = 0,75, реализован в скрипте) по тексту резюме, в том числе заявленный
  грейд, на всём пуле специализации;
* **BM25 + наши фильтры** — тот же пул, что видит наш подбор, но в порядке BM25. Так видно,
  что даёт именно формула скоринга;
* **/eval/rank** — наш текстовый ранжировщик для внешних резюме;
* **случайный порядок**.

Holdout, основная разметка, 210 потребностей:

| Система | P@10 | nDCG@10 | MRR@10 |
|---|---|---|---|
| **Наш подбор** | **0,669** (0,641–0,697) | **0,579** (0,559–0,597) | **0,896** (0,864–0,927) |
| BM25 + наши фильтры | 0,482 (0,454–0,511) | 0,417 (0,393–0,442) | 0,634 (0,588–0,679) |
| BM25 | 0,361 (0,333–0,391) | 0,309 (0,284–0,334) | 0,558 (0,509–0,606) |
| /eval/rank (только текст) | 0,391 (0,365–0,417) | 0,331 (0,308–0,356) | 0,553 (0,503–0,606) |
| Случайный | 0,216 | 0,157 | 0,390 |

Парные разности на holdout:
* наш подбор − BM25: nDCG +0,270 (0,246…0,293), P@10 +0,308 (0,277…0,339);
* наш подбор − BM25 на том же пуле: nDCG +0,162 (0,140…0,183), P@10 +0,187 (0,158…0,214);

Выигрыш у BM25 складывается из двух частей: пул (фильтры по категории с допуском на грейд ниже
и must-навыкам) и сама формула скоринга. На одном и том же пуле формула обходит BM25 на
+0,128 nDCG: она учитывает подтверждённую категорию, перцентиль, ФСП и смежные навыки.

`/eval/rank` для внешних резюме обходит простой BM25: nDCG@10 0,331 против 0,309,
P@10 0,391 против 0,361. Раньше он проигрывал (0,292): навыкам из словаря давалось 60% веса,
а заявленный грейд почти не учитывался. Теперь веса такие: навыки 37,5, BM25 25, грейд из резюме 25
(на грейд ниже — сильный штраф, переквалификация — слабый), условия 10, отрасль 2,5. Веса выбраны
на dev по сетке, цифры выше — holdout.

### Абляции (holdout)

| Без сигнала | P@10 | nDCG@10 | Разность с полной моделью: nDCG / P@10 |
|---|---|---|---|
| — (полная) | 0,669 | 0,579 | |
| без теста | 0,450 | 0,438 | +0,141 (0,120…0,164) / +0,220 (0,195…0,243) |
| без ФСП | 0,665 | 0,580 | −0,001 (−0,006…0,004) / +0,004 (−0,003…0,011) |
| без регулярных задач | 0,662 | 0,579 | −0,000 (−0,006…0,005) / +0,007 (−0,002…0,016) |

«Без теста» значит, что категория берётся из заявленного в резюме грейда, перцентиль равен 50
для всех, подтверждённых тестом навыков нет, видны все кандидаты. Такого режима в продукте нет:
без теста кандидат в поиск не попадает.

* **Тест** — главный сигнал: +0,14 nDCG и +0,22 P@10 к ранжированию по заявленному грейду.
  По строгой и мягкой разметкам вывод тот же (nDCG 0,536 против 0,437 и 0,618 против 0,432).
  Подтверждённый грейд всё ещё чаще занижен, чем завышен (holdout: верный у 785, на ступень
  ниже у 563, на две ниже у 36, выше у 98). Поэтому жёсткие фильтры прячут 65% релевантных
  кандидатов, и это главный резерв.
* **ФСП** — вклад в пределах шума. На банке v3 множитель 0,3 давал +0,011 P@10 (значимо), на
  банках v4 и v6 — около нуля (на v6 nDCG −0,001, интервал −0,006…0,004; P@10 +0,004, интервал −0,003…0,011). Достижения ФСП в генераторе
  коррелируют с θ, и их информация почти полностью дублирует тест. Пробовали усиливать ФСП
  при неточном тесте (бонус × (1 − 0,6 × надёжность перцентиля)): +0,003 nDCG на dev и +0,001
  на holdout, незначимо, поэтому не взяли. Бонус ФСП оставлен как объяснимый сигнал внутри
  категории: он нужен там, где теста мало, а в симуляции тест есть у всех.
* **Регулярные задачи** — по nDCG вклад нулевой (+0,002, незначимо), по P@10 +0,013 (значимо).
  В симуляции задачи зависят только от θ и активности, а не от навыков потребности.

### Подбор весов формулы

### Смежные навыки по таксономии

Если у кандидата нет нужного навыка, но есть навык той же компетенции из таксономии (например,
другой фреймворк того же слоя), он получает 0,25 от веса навыка (0,375 для подтверждённого) и
объяснение «X вместо Y». Вес выбран на dev по сетке 0 / 0,15 / 0,25 / 0,4. Эффект на синтетике
нейтральный (±0,002 nDCG): генератор выбирает навыки кандидата независимо от компетенций, поэтому
смежность в нём не несёт сигнала. На реальных стеках навыки одной компетенции связаны, и эффект
нужно проверить на пилоте.

### Изменение формулы (одно)

Цифры этого раздела получены до исправления покрытия: изменение формулы делалось раньше.

Первый прогон показал, что внутри пула, прошедшего фильтры, наша формула упорядочивает
кандидатов **хуже** BM25: на holdout nDCG 0,372 против 0,397. Больше всего мешал перцентиль. На
dev его корреляция с золотой меткой внутри пула отрицательная (−0,10), а весит он 26 баллов
из 100.

Объяснение простое. Внутри одной категории шириной 0,8 истинный разброс θ равен
τ² = 0,8²/12 ≈ 0,053, а ошибка теста SE² ≈ 0,25. Надёжность внутрикатегорийного перцентиля
ρ = τ²/(τ² + SE²) ≈ 0,2, то есть примерно на 80% он шум. Изменение в `strength()`
(`src/matching/matching.ts`): перцентиль сжимается к 50 с коэффициентом ρ, который считается по
SE самого кандидата. Свободных параметров нет, τ берётся из ширины грейда. На карточке и в
объяснении по-прежнему показан исходный перцентиль, в evidence добавлен множитель.

| | dev, до → после | holdout, до → после |
|---|---|---|
| nDCG@10 | 0,370 → 0,403 | **0,372 → 0,409** |
| P@10 | 0,488 → 0,496 | 0,503 → 0,516 |
| MRR@10 | 0,742 → 0,801 | 0,750 → 0,795 |
| nDCG@10, строгая разметка | 0,252 → 0,311 | 0,247 → 0,305 |
| nDCG@10, мягкая разметка | 0,502 → 0,498 | 0,515 → 0,518 |

Решение принималось по dev, holdout подтвердил результат. По мягкой разметке, где
переквалификация не штрафуется, изменение нейтрально. Цифры «до» получены на коде коммита
24c1668. Чтобы их воспроизвести, верните прежний `strength()` и запустите `npm run eval`. Тесты
обновлены: добавлена проверка, что при меньшем SE перцентиль весит больше.

## Ограничения и что не проверено

* В банке ещё 48 семейств, ответ которых по дампу из 300 экземпляров угадывается чаще чем в
  половине случаев (см. «Слив банка»). Канарейки ловят только явные случаи.
* Нет ни одного реального кандидата. Экспертные `b` банка не откалиброваны, а истинные
  параметры в симуляции — это экспертные плюс шум, не данные.
* В части «Тест» модель одномерная, как у оценщика. Тест получается проще реальности.
* Практическое задание с кодом и вопрос о подходе не моделируются, хотя в продакшене при
  включённой песочнице они влияют на итог.
* Нет временных эффектов: окна экспозиции в 90 дней, кулдаунов пересдачи, параллельных сессий.
* Разметку подбора придумали мы. Вывод о вкладе теста и ФСП зависит от того, как штрафовать
  переквалификацию, поэтому приведены три разметки.
* Поведение накрутчиков упрощено: копирование чужих резюме, подмена личности и списывание по
  ходу теста не моделируются.
* Зарплата, отрасль и формат в разметку не входят. Их вклад в формулу этот отчёт не оценивает и
  скорее штрафует как шум.
