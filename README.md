# Скаут × ФСП — обратный найм в ИТ

Кандидат проходит адаптивный тест и получает подтверждённую категорию «специализация · грейд» с перцентилем.
Работодатель ищет по подтверждённым категориям, видит объяснение ранжирования и приглашает с обязательной вилкой.
Контакты кандидата открываются только после принятия инвайта.

## Проверьте нас за 5 минут

**Стенд:** https://scout.141.133.201.48.sslip.io (HTTPS). Входы для жюри — кнопки на странице входа,
пароль `demo12345`: у каждого проверяющего своя пара `juryN-candidate@demo.ru` и `juryN-employer@demo.ru`.
Демо-видео (7 минут, весь сценарий одной записью со стенда) приложено к заявке.

| Шаг | Что сделать | Что увидеть |
|---|---|---|
| 1. Механика теста | Меню → «Как работает тест» (`/how-it-works`) | Как выбирается следующее задание по текущей оценке уровня и когда тест останавливается |
| 2. Тест | «Экспресс-тест для жюри (5 минут)» на главной → согласия → опрос → грейд → «Экспресс-тест для жюри» | Адаптивный выбор заданий; у каждого кандидата свои числа и формулировки. Экспресс-режим категорию не присваивает |
| 3. Подбор | Работодатель «Жюри N» → «Новая потребность» → описать обычным текстом → «Разобрать» → «Подтвердить и показать категории» → «Собрать подборку» | Текст разобран в фильтры; поиск по подтверждённым категориям среди 420 синтетических кандидатов; «Подробнее» раскладывает балл по факторам |
| 4. Инвайт | «Открыть карточку» → «Пригласить» | Анонимная карточка, обязательная вилка; контакты закрыты до согласия кандидата |
| 5. Свои данные | «Проверка подбора на своих резюме» на главной (`/evaluate`, вход работодателем) | Ранжирование ваших резюме с вкладом факторов и метриками nDCG@10, Recall@10, RR@10 по вашей разметке |
| 6. API | `/api-docs/` — Swagger UI по спецификации `/api/v1/openapi.json` | Все методы с запросами, ответами и кодами ошибок |

Полный путь с присвоением категории и раскрытием контактов: кандидат «Жюри N» проходит полный тест
(около 25 минут: 8–14 адаптивных заданий, задача с кодом в песочнице Piston и вопрос о своём решении),
работодатель «Жюри N» находит его в подборке и приглашает, кандидат принимает инвайт в разделе «Инвайты».
Регистрация нового кандидата с подтверждением почты на стенде тоже работает.

## Запуск одной командой

Нужен Docker с Compose v2. Порты 5432, 6379, 8000, 8025, 8080 и 8081 должны быть свободны.

```bash
cd infra
cp .env.example .env
docker compose up --build
```

Первый запуск занимает несколько минут. Когда в логах появится `web` и `api` станет healthy, откройте:

| Что | Адрес |
|---|---|
| Приложение | http://localhost:8081 |
| Keycloak (admin / admin12345) | http://localhost:8080 |
| Почта регистрации (Mailpit) | http://localhost:8025 |
| API | http://localhost:8081/api/v1 (напрямую: http://localhost:8000/api/v1) |

Если порт 5432 занят локальным PostgreSQL, задайте в `.env` `POSTGRES_HOST_PORT=5433`.

## Сценарий проверки

1. Войти как `juryN-candidate@demo.ru`: согласия → опрос → тест → результат с категорией и перцентилем.
2. Войти как `juryN-employer@demo.ru` (лучше в другом браузере или инкогнито): «Новая потребность» или «Банк кандидатов» → карточка → инвайт с вилкой.
3. Снова кандидатом: «Инвайты» → принять. Работодатель видит контакты в карточке кандидата.

## Валидация

`cd backend && npm run eval` прогоняет боевой тест и подбор на синтетике (2000 кандидатов, seed зафиксирован, генератор ответов независим от оценщика). Полный отчёт: [docs/validation.md](docs/validation.md).

Синтетика у каждой команды своя, поэтому абсолютные цифры разных решений напрямую не сравниваются. Каждая метрика ниже стоит рядом с базовой линией, посчитанной на тех же данных.

| Что проверяли | Скаут | Базовая линия на тех же данных |
|---|---|---|
| Подбор, nDCG@10 (holdout, 210 потребностей, веса подобраны на отдельной dev-выборке) | **0,579** | BM25 по резюме 0,309 (+87%); BM25 с теми же жёсткими фильтрами 0,417 (+39%) |
| Подбор, P@10 / MRR@10 | **0,669 / 0,896** | BM25 0,361 / 0,558 |
| Вклад теста в подбор | **+0,141** nDCG@10 | та же формула без результатов теста 0,438 |
| Тест: грейд ±1 ступень | **98,2%** | — |
| Тест: точный грейд из 5 классов / κ | 57,0% / 0,81 | фиксированная форма из 12 заданий того же банка 52,4% / 0,76 |
| Итоговый грейд в продуктовом сценарии (с пересдачей ступенью ниже) | 62,7% точно, **99,6%** ±1, κ 0,85 | — |
| Повторный тест другой формой, κ | 0,71 | — |
| Ложные отказы / ложные подтверждения | 22,8% / 23,8% | — |
| Слив всех ключей: завышение θ̂ | **+0,62** | фиксированный тест +2,68 |
| Угадывание ответа по дампу банка | 26% в среднем | 52% до пулов формулировок с разными правильными вариантами |
| Канарейки: ложные флаги у честных кандидатов | 0% | — |

Вклад ФСП в подбор на синтетике незначим: P@10 +0,004 (−0,003…0,011), потому что тест уже измеряет то же умение. По итогам валидации исправлен обрыв сессий на обязательном покрытии редких компетенций (было 48% сессий).

## LLM

GigaChat-2-Max пишет только черновики новых заданий: `cd backend && npm run llm:drafts`. Эталон пересчитывает код, затем слепое решение и рецензент; в банк черновик попадает лишь после экспертной проверки. Ответы кандидатов модель не видит. Подробнее: [docs/technical-guide.md](docs/technical-guide.md#какие-модели-как-и-зачем).

## Подбор

Поиск сохраняет обязательные навыки, специализацию, согласие на публикацию,
приватность компании и условия работы как строгие ограничения. Кандидаты
на один грейд ниже выбранного показываются со штрафом 15 баллов и отдельной
пометкой в карточке. Их подтверждённая категория не меняется.
Достижение доли скрытых релевантных ≤30% требует независимой разметки.

`/evaluate` после входа работодателя позволяет ранжировать собственные резюме
и видеть вклад каждого фактора. Используется реальный `/api/v1/eval/rank`;
мок-режим страницы отключён. Необязательная полная разметка 0–4 позволяет
рассчитать nDCG@10, Recall@10 и RR@10; без разметки метрики не показываются.
На синтетике текстовый ранжировщик обходит BM25: nDCG@10 0,331 против 0,309, P@10 0,391 против 0,361.
